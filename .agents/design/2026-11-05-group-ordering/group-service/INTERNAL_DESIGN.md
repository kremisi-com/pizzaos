# Dettagli interni

Persist `groups` as optional state extension in canonical repository. Each record stores host account id, invitation secret hash plus host-recoverable invitation, personal token hashes, roster, deadline, revision, private `canonicalKey` and optional frozen checkout request. Generate randomBytes(32) tokens, randomUUID ids; compare token hashes, never trust public participantId. The canonical key is independently generated with randomBytes(32) at collection creation, persisted server-side and excluded from every DTO; a caller-selected individual checkout key or public group id cannot predict or occupy it. Return explicitly assembled DTOs. Validate exact keys/types on service and HTTP boundaries before Ajv coercion; guard prototype-key ids and all sizes.

Every access/mutation expires group under repository lock. tick scans groups; no payment side effect. Expiry must commit even if a later mutation fails: perform expiry in a separate transaction before work, and also check current clock inside mutations to close races. Membership checks derive from actor id or hash-scoped cookie. Reject guests on closed, host may correct before checkout. Revision checks prevent replacement races.

Flatten participant lines in stable roster order, prefix notes with `Per <name> · ` (length bounded). This keeps explicit participant attribution visible in existing canonical restaurant UI without changing its private implementation. Build cart server-side from shared storeId/lines and host fulfillment; canonical quote and checkout calculate all economic behavior. Quote records no reservations. Host verifies each new quote explicitly.

Before external canonical checkout, save frozen original input/cart. Block edits; identical retries reuse the collection's private persisted `canonicalKey`. Invoke canonical ordering.checkout outside repository transaction with that key, then atomically link resulting order. All read recovery, submission and error recovery lookups use this same private field, never `group:<publicGroupId>` or the browser's idempotency key. If throw, inspect canonical idempotency entry under lock: if order exists keep frozen input and discover order on later read/retry; if definitive 4xx before order creation clear frozen claim. Transient failure retains claim. If process dies before invoking canonical, retry runs frozen original request. Canonical key is persisted and unique for group; no second order can be created. Decorator analytics receives canonical order as usual. Submitted snapshot/orderId resolves existing idempotency on read; guest DTO never includes order or checkout data.

HTTP extracts per-group HttpOnly cookie and uses authenticated actor. Issuing capability happens only after join; cookie forwarding already exists. Routes register in production server beside pilot extensions and isolated E2E fixture. Worker calls groups.tick. No SQL migration needed, existing snapshot retains fields across instances.

Checklist: authenticated create; guest minimization; secure scoped capability; host removal; bounded hostile inputs; revisions; deadline race and worker; no precheckout reservations; canonical conflicts; immutable attribution; exact retry and crash recovery; proxy/demo/cookie protections; no external credentials/test identities.
