# Requisiti osservabili

1. Le analytics e le consegne devono leggere e modificare lo stesso stato durevole del servizio ordini; dopo ricostruzione dei servizi sul repository restano assegnazioni, problemi e dati analytics.
2. L'operatore abilita un rider e assegna un ordine delivery pronto. Il rider autenticato può leggere solo le proprie consegne e compiere dispatch e complete, con controllo dell'assegnazione al momento della transizione. Complete aggiorna l'ordine canonico, scala le scorte riservate una volta, marca i contanti incassati secondo il contratto ordini e alimenta le analytics alla data di completamento.
3. La route generica /v1/pilot/orders/:id/actions continua a negare azioni operative al rider di una consegna altrui al suo account cliente; non deve restituirgli IndividualOrder. Nessun allargamento delle API generiche ordini, eventi, configurazioni o analytics al ruolo rider.
4. Le route rider non restituiscono email del cliente, riferimenti provider, stato rimborsi o modelli di ordine completi. Dispatch/complete/failure restituiscono 204. Sessione anonima è leggibile e indica assenza attore; le consegne senza login restituiscono 401. Identità autenticata senza appartenenza rider riceve 403 per le operazioni rider.
5. Un problema delivery resta aperto, visibile all'operatore e impedisce completamento dal rider finché l'operatore riassegna (anche allo stesso rider). Un annullamento operatore usa il normale rimborso; ordine annullato scompare dalle consegne rider attive.
6. Le route estensioni ereditano il controllo proxy/autenticazione di buildOrderingApp. Corpo/query non validi danno 400, assenza login 401, permessi mancanti 403, risorsa assente 404, conflitto 409. Errori inattesi non espongono dettagli interni.
7. Una sede può avere timeZone IANA configurato; valori non validi sono rifiutati al salvataggio. Le sedi esistenti senza campo usano Europe/Rome per compatibilità. Il fuso si configura dall'admin, non dal codice frontend.
